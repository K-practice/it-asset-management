以下の既存要件も引き継ぐ。

- 管理担当者が機器・場所・アカウントを管理し、一般利用者は全社の機器の現在情報を閲覧する。
- 個人割当はアカウントを持つ社員1人に限定する。共有・未割当も扱う。
- 機器は論理削除して復元できる。廃棄とは区別する。
- アカウント無効化・場所の利用停止では、既存の機器情報を保持する。
- アカウント再有効化・場所の利用再開を初期版に含める。
- 初回・パスワードリセット後は、本人によるパスワード変更を必須にする。
- 履歴の閲覧・CSV出力・更新操作は管理担当者のみ。

要件定義書の本文v1.2・画面設計書の本文v1.2と整合させている。既存ファイル名は継続使用し、本文の表で版数を管理する。デザイン・画面構成の変更は、DBの権限を変更する根拠にしない。

## 2. テーブル構成【初期案】

| テーブル名 | 論理名 | 役割 |
|---|---|---|
| users | 社員・アカウント | 社員情報、認証、権限、有効状態 |
| locations | 場所 | 部屋・エリアの名称、利用状態 |
| asset_number_sequences | 種別別採番管理 | PC・ネットワーク機器ごとの最後の発行番号 |
| assets | 機器 | 現在の機器情報、所在、割当、状態 |
| asset_change_histories | 機器変更履歴 | 5項目の変更内容・変更者・日時 |

採番管理は、機器登録・種別変更の処理から利用する内部テーブルとする。

種別・機器状態・利用者区分・権限・履歴項目は、固定の数値コードとして管理する初期案。CHECK制約とアプリの定義を合わせ、専用マスターテーブルは追加しない。

## 3. 共通の物理設計方針【初期案】

| 項目 | 方針 |
|---|---|
| ストレージエンジン | 全テーブルInnoDB |
| 文字コード | utf8mb4 |
| 照合順序 | utf8mb4_binを基本とする |
| 主キー | INT。採番管理以外はAUTO_INCREMENT |
| IDの型 | 外部キーを含めてSIGNEDのINTに統一 |
| 任意文字列 | 未登録はNULL。空文字とNULLを混在させない |
| 日時 | DATETIME、秒まで記録 |
| 日時の運用 | 日本時間に統一する初期案。接続・アプリの設定をそろえる |
| 物理削除 | 通常の画面操作では実施しない |
| 外部キーの削除・更新動作 | 原則ON DELETE RESTRICT／ON UPDATE RESTRICT |
| 制約名 | テーブル名を含む名前とし、DB内で重複させない |
| 文字数 | 本書のVARCHAR上限は初期案。入力検証にも同じ上限を適用 |
| 初期データ | 種別別採番の2行と、初期管理担当者をセットアップで作成 |

PRIMARY KEY・FOREIGN KEY・UNIQUE・CHECKを用途に応じて使う。NOT NULLを併用し、未入力の必須値をCHECKだけで扱わない。

基本の照合順序による暗黙の大文字・小文字判定には依存せず、ログインID専用の小文字キーを使う。ログインIDは半角英数字と . _ - のみで空白禁止【確定】。文字種をアプリで検証し、DB側の制約もSQL作成時に具体化する。全角文字を半角へ自動変換して許可しない。

日付の初期値CURRENT_TIMESTAMPは、接続時刻設定と合わせて使う。更新日時はアプリが更新時に明示設定する初期案で、作成時の初期値と混同しない。

## 5. users：社員・アカウント

### 5.1 テーブル定義【初期案】

| No. | 論理名 | 物理名 | 型 | NULL | キー・制約 | 初期値 | 説明 |
|---|---|---|---|---|---|---|---|
| 1 | 社員ID | user_id | INT | 不可 | PK、AUTO_INCREMENT | 自動 | 内部の識別ID |
| 2 | 社員名 | user_name | VARCHAR(100) | 不可 | 空文字不可 | なし | 氏名。名前の重複は許可 |
| 3 | ログインID | login_id | VARCHAR(64) | 不可 | 空文字不可 | なし | 入力された表示用ID |
| 4 | ログイン検索キー | login_id_key | VARCHAR(64) | 不可 | UNIQUE、小文字整合CHECK | なし | login_idの小文字版 |
| 5 | パスワードハッシュ | password_hash | VARCHAR(255) | 不可 | 空文字不可 | なし | ハッシュ化した値 |
| 6 | 権限 | role | INT | 不可 | CHECK：1、2 | 1 | 一般利用者／管理担当者 |
| 7 | 有効状態 | is_active | INT | 不可 | CHECK：0、1 | 1 | 無効化しても社員情報は残す |
| 8 | パスワード変更必須 | must_change_password | INT | 不可 | CHECK：0、1 | 1 | 初回・リセット後は1 |
| 9 | ログイン状態版数 | session_version | INT | 不可 | CHECK：1以上 | 1 | 既存ログイン無効化用の実装初期案 |
| 10 | 登録日時 | created_at | DATETIME | 不可 |  | CURRENT_TIMESTAMP | 登録時刻 |
| 11 | 更新日時 | updated_at | DATETIME | 不可 |  | CURRENT_TIMESTAMP | アプリが更新時に設定 |

### 5.2 ログインIDの扱い

- login_idには表示用の表記を保存する。
- login_id_keyには、同じログインIDをMariaDBのLOWERで小文字化した値を保存する。
- UNIQUEはlogin_id_keyに設定する。
- ログイン検索も同じLOWERを使う。アプリ独自の別の正規化と混在させない。
- Yamadaを登録済みなら、yamada・YAMADAは同じキーとなり、別アカウントとして登録できない。
- 無効なアカウントのキーも重複禁止とする初期案。復帰は既存アカウントの再有効化で扱う。
- user_idは名称・ログインIDとは別の、変更しない内部IDとする。

小文字化はカラムのデータ型ではなく、値を整える処理である。2つのカラムはどちらもVARCHARを使用する。

整合性のCHECK案：

~~~sql
CHECK (login_id_key = LOWER(login_id))
~~~

許可文字は半角英数字と . _ - のみで、空白・日本語・全角文字は禁止【確定】。ログイン入力と作成入力で同じ文字種検証を使用する。小文字化以外の自動変換は行わない初期案。

### 5.3 初期管理担当者

初期セットアップでrole=2、is_active=1、must_change_password=1の管理担当者を1人作成する。パスワードはアプリと同じ方式でハッシュ化する。平文のパスワードをこのテーブルに保存しない。

アカウント無効化はis_activeの更新で行う。社員の削除による履歴・割当の消失を避ける。

### 5.4 氏名編集・パスワード・ログイン状態

登録済みアカウントはuser_nameのみ編集できる【確定】。内部user_id・ログインID・権限・割当を維持する。履歴内の社員名・変更者名は更新しない。

パスワードは15〜64文字、文字種の組み合わせは強制しない【確定】。平文の文字数と、VARCHAR(255)に保存するハッシュ文字列の長さは別である。ハッシュ方式と許可文字の詳細はアプリ実装で具体化する。

リセット時に全既存ログインを無効にする動作は確定。これを実現する実装初期案としてsession_versionを追加する。usersは11カラムとなり、全5テーブルで合計46カラムとなる。

- ログイン時のセッションにはuser_idと、その時点のsession_versionを保持する。
- 各認証済み要求で、現在の有効状態・版数・変更必須状態をサーバー側で確認する。
- リセットではpassword_hash更新、must_change_password=1、session_versionの加算を同一トランザクションで行う。既存の版数のセッションは次のアクセスを拒否する。
- 30分の無操作タイムアウトはセッションとアプリで管理する。版数は操作時刻ではないため、アクセスのたびに加算しない。
- 無効化時にも版数を加算し、再有効化だけで古いセッションが復活しない方式を初期案とする。
- 本人の通常パスワード変更では他の既存セッションを無効にし、現在の認証済みセッションを更新する初期案。初回・リセット後の変更でも変更必須を解除して版数を更新する。
- 版数の更新はDB上で原子的に加算し、上限・失敗では途中の変更だけを確定しない。

この版数は画面・CSVに表示しない。セッション方式そのものは開発準備で選定する。自動ログアウトで未保存のフォームを自動送信しない。

## 6. locations：場所

| No. | 論理名 | 物理名 | 型 | NULL | キー・制約 | 初期値 | 説明 |
|---|---|---|---|---|---|---|---|
| 1 | 場所ID | location_id | INT | 不可 | PK、AUTO_INCREMENT | 自動 | 内部の識別ID |
| 2 | 場所名 | location_name | VARCHAR(100) | 不可 | UNIQUE、空文字不可 | なし | 部屋・エリア名 |
| 3 | 利用状態 | is_active | INT | 不可 | CHECK：0、1 | 1 | 利用中／利用停止 |
| 4 | 登録日時 | created_at | DATETIME | 不可 |  | CURRENT_TIMESTAMP | 登録時刻 |
| 5 | 更新日時 | updated_at | DATETIME | 不可 |  | CURRENT_TIMESTAMP | アプリが更新時に設定 |

- UNIQUEを有効状態に関係なく適用し、停止した場所と同じ名前の新規登録も禁止する。
- 場所の利用再開は同じlocation_idのis_activeを1に戻す。
- 名称変更でもlocation_idを維持する。
- 機器の設置数はassetsから集計し、件数カラムとして重複保存しない。
- 履歴内の過去の名称は、場所名変更に合わせて書き換えない。
- 住所・拠点・棚・座席の専用カラムは設けず、所在補足は機器側に保存する。

場所名は前後の空白を除去して保存・比較し、英字の大小文字を区別する【確定】。前後空白だけの名前は必須エラーとする。現在のUNIQUE案はutf8mb4_binを使用し、RoomAとroomaを別名として扱う。空白除去後の名称にDBのUNIQUEを適用し、停止済みも同名登録を拒否する。内部の空白・全角半角は追加の正規化を行わない初期案。SQL作成時に前後空白・英字の大小文字・日本語名の境界を実機確認する。

## 7. asset_number_sequences：種別別採番管理

| No. | 論理名 | 物理名 | 型 | NULL | キー・制約 | 初期値 | 説明 |
|---|---|---|---|---|---|---|---|
| 1 | 機器種別 | asset_type | INT | 不可 | PK、CHECK：1、2 | なし | PC・ネットワーク機器の区分 |
| 2 | 最終発行連番 | last_number | INT | 不可 | CHECK：0以上 | 0 | この種別で最後に発行した連番 |
| 3 | 更新日時 | updated_at | DATETIME | 不可 |  | CURRENT_TIMESTAMP | 採番時に更新 |

初期データ：

| asset_type | last_number |
|---|---|
| 1 | 0 |
| 2 | 0 |

last_number=0は、その種別でまだ番号を発行していないことを表す。

### 7.1 採番方法【初期案】

1. トランザクションを開始する。
2. 対象種別の行をSELECT ... FOR UPDATEでロックする。
3. last_number+1を新しいsequence_numberとする。
4. 種別の接頭辞と連番からmanagement_numberを作る。
5. 採番管理・機器・必要な履歴を更新し、まとめてコミットする。
6. 失敗時はまとめてロールバックする。

FOR UPDATEはトランザクション内で利用する。採番管理を先に確定してから機器を別処理で登録しない。

確定した発行済み番号は、論理削除や種別変更によって巻き戻さず再利用しない。ロールバックで一度も確定しなかった番号とは区別する。

採番管理行はアプリの通常操作で削除・初期化しない。再セットアップ時に既存のカウンターを0へ上書きしない。

### 7.2 表示形式【桁数の細部は初期案】

- PCの1番目：PC-000001。
- ネットワーク機器の1番目：NET-000001。
- 連番は最低6桁にゼロ埋めする。
- 1000000以降は桁を増やし、番号を切り捨てない。
- 正のSIGNED INTの範囲内で扱い、上限での採番はエラーとして止める。

SQLでゼロ埋めする場合、LPADの長さを固定6にして7桁以上を切り詰めない。アプリの書式化と同じ結果になることを確認する。

| 14 | 備考 | notes | VARCHAR(1000) | 可 |  | NULL | 任意の補足情報 |
| 15 | 論理削除状態 | is_deleted | INT | 不可 | CHECK：0、1 | 0 | 通常一覧・CSVからの除外 |
| 16 | 更新版数 | row_version | INT | 不可 | CHECK：1以上 | 1 | 同時編集の検知用の初期案 |
| 17 | 登録日時 | created_at | DATETIME | 不可 |  | CURRENT_TIMESTAMP | 初回登録時刻 |
| 18 | 更新日時 | updated_at | DATETIME | 不可 |  | CURRENT_TIMESTAMP | 編集・削除・復元時に更新 |

### 8.1 管理番号の整合性

management_numberは、採番で決まったasset_type・sequence_numberからアプリが生成して保存する初期案。AUTO_INCREMENTのasset_idから発行する方式は使わない。

DBには以下を設定する。

- UNIQUE(management_number)。
- UNIQUE(asset_type, sequence_number)。
- CHECK(sequence_number >= 1)。
- 種別と連番から期待する番号に一致するCHECK。

書式整合の式の案：

~~~sql
management_number = CONCAT(
    CASE asset_type WHEN 1 THEN 'PC-' WHEN 2 THEN 'NET-' END,
    LPAD(sequence_number, GREATEST(6, CHAR_LENGTH(sequence_number)), '0')
)
~~~

アプリの生成結果とDBの式をそろえる。SQL作成時に1・999999・1000000を含む境界値を実機確認する。

### 8.2 個人利用・共有・未割当

~~~sql
CHECK (
    (assignment_type = 1 AND assigned_user_id IS NOT NULL)
    OR
    (assignment_type IN (2, 3) AND assigned_user_id IS NULL)
)
~~~

共有・未割当で、以前の社員IDを残さない。個人利用で社員IDを省略しない。

### 8.3 状態と利用者区分

~~~sql
CHECK (
    (status <> 1 OR assignment_type IN (1, 2))
    AND
    (status <> 4 OR assignment_type = 3)
)
~~~

使用中は個人利用または共有、廃棄は未割当とする。保管中・故障では区分を限定しない。

状態を変更しただけで割当を自動解除せず、入力がこの条件に合わなければ修正を求める。廃棄から他の状態への訂正を許可する【確定】。訂正時も同じ条件を満たし、状態や利用者の変更履歴を保存する。

### 8.4 種別変更

- asset_idを維持する。
- 変更先種別のカウンターから新しいsequence_numberを発行する。
- management_numberを変更先種別の番号へ更新する。
- 種別変更・管理番号変更の2項目を履歴に保存する。
- 同じ種別のまま保存した場合は再発行しない。
- 再び元の種別へ戻しても、その種別の新しい番号を発行する。
- 以前の管理番号へ戻したり、旧番号を別の機器に付けたりしない。

例：

| 操作 | asset_id | 種別 | 管理番号 |
|---|---|---|---|
| PCとして登録 | 10 | PC | PC-000001 |
| ネットワーク機器へ変更 | 10 | ネットワーク機器 | NET-000001 |
| PCへ戻す | 10 | PC | PC-000002 |

例は各種別のカウンターにほかの発行がない場合。現物ラベルの貼り替えは管理担当者の運用とする。

### 8.5 削除・復元

論理削除はis_deleted=1、復元は0への更新。asset_id・現在の番号・所在・割当・履歴を保持する。

削除済み機器も管理番号と種別内連番のUNIQUE対象に含める。復元では新しい番号を発行しない。廃棄はstatus=4であり、is_deletedとは別の状態。

削除日時・削除者の専用カラムは、今回の設計には追加していない。更新日時を削除日時と誤って表示しない。

### 8.6 同時編集【拒否する動作は確定・方式は初期案】

row_versionは画面入力項目ではなく、取得したデータの版数として利用する。

保存時は、取得時の版数と現在の版数が一致することを確認し、成功時に1増やす。別の操作が先に更新していた場合は保存を止め、最新情報の確認を求める。

日時だけで更新競合を判定しない。秒が同じでも別の更新になり得るため、履歴の並びにもhistory_idを併用する。

## 9. asset_change_histories：機器変更履歴

| No. | 論理名 | 物理名 | 型 | NULL | キー・制約 | 初期値 | 説明 |
|---|---|---|---|---|---|---|---|
| 1 | 履歴ID | history_id | INT | 不可 | PK、AUTO_INCREMENT | 自動 | 履歴の識別ID |
| 2 | 機器ID | asset_id | INT | 不可 | FK | なし | 対象機器の内部ID |
| 3 | 変更項目 | change_type | INT | 不可 | CHECK：1〜5 | なし | 場所・利用者・状態・種別・管理番号 |
| 4 | 変更前の表示内容 | before_value | VARCHAR(512) | 不可 | 空文字不可 | なし | 変更当時の内容 |
| 5 | 変更後の表示内容 | after_value | VARCHAR(512) | 不可 | 空文字不可 | なし | 変更当時の内容 |
| 6 | 変更者社員ID | changed_by_user_id | INT | 不可 | FK | なし | 実行した管理担当者 |
| 7 | 変更者名の当時値 | changed_by_name | VARCHAR(100) | 不可 | 空文字不可 | なし | 実行時の社員名 |
| 8 | 変更者ログインIDの当時値 | changed_by_login_id | VARCHAR(64) | 不可 | 空文字不可 | なし | 実行時の表示用ログインID |
| 9 | 変更日時 | changed_at | DATETIME | 不可 |  | CURRENT_TIMESTAMP | 変更時刻 |

### 9.1 保存単位【初期案】

1回の更新で、変わった項目ごとに1行保存する。種別変更で番号も変わった場合は2行になる。複数行は機器更新と同じトランザクションで確定する。

同じ値のまま保存した項目には行を作らない。初回登録は変更履歴を作らず、assets.created_atに登録日時を保存する【確定】。

保存済みの履歴はアプリから編集・削除しない。機器の論理削除、場所名変更、アカウント無効化後も残す。

### 9.2 表示内容の例

| change_type | before_value | after_value |
|---|---|---|
| 1：場所 | 倉庫 | 執務室 |
| 2：利用者 | 未割当 | 個人利用：山田太郎（yamada） |
| 2：利用者 | 個人利用：山田太郎（yamada） | 共有 |
| 3：状態 | 保管中 | 使用中 |
| 4：種別 | PC | ネットワーク機器 |
| 5：管理番号 | PC-000001 | NET-000001 |

表示文言の具体形は初期案。社員名にはログインIDを添えることで、同じ氏名の社員を区別できる。

前後の値は現在のマスター名への参照だけにせず、文字列として保存する。表示文字列は履歴を読むための情報として扱い、解析して通常の外部キーの代わりに使わない。

変更者はchanged_by_user_idで現在も同じ社員に関連付け、画面の名前はchanged_by_name・changed_by_login_idから当時値を表示する。

### 9.3 保持する履歴の範囲

メーカー・型番・シリアル番号・所在補足・備考、パスワード、削除・復元、マスター名称変更の操作自体は、この履歴テーブルの対象に追加しない。

場所名を変更しただけで、関連する全機器の場所変更履歴を一斉に作らない初期案。過去に記録された文字列は書き換えない。

旧管理番号から機器を探す追加の画面機能は、本設計だけを根拠に追加しない。DB上はchange_type=5の履歴とasset_idから番号変更の関連を確認できる。

## 12. DBとアプリの役割

| ルール | 主に担う層 |
|---|---|
| 主キー・管理番号・種別内連番の重複禁止 | DB |
| 場所名・小文字ログインキーの重複禁止 | DB |
| 参照する機器・社員・場所が存在すること | DB |
| 状態・区分・フラグの値の範囲 | DB＋アプリ |
| 個人利用の社員必須、共有・未割当の社員なし | DB＋アプリ |
| 使用中・廃棄と利用者区分の整合 | DB＋アプリ |
| 表示番号と種別・連番の一致 | DB＋アプリ |
| 停止場所・無効な社員の新規選択禁止 | アプリのトランザクション |
| 既存の停止・無効値を保持した編集・復元 | アプリ |
| 最後の有効管理担当者の無効化禁止 | アプリのトランザクション |
| 未ログイン・一般利用者の操作制限 | アプリ |
| 初回・リセット後のパスワード変更必須 | アプリ |
| リセット前の全既存ログインの無効化 | session_versionとアプリの実装初期案 |
| 無操作30分でのログアウト | セッションとアプリ |
| 同時編集の検知 | row_versionとアプリ |
| 変更当時の名称の取得・履歴生成 | アプリのトランザクション |

### 12.1 停止・無効情報

- 新しい機器の登録では利用中の場所と、有効な個人割当先を選ぶ。
- 編集で場所ID・割当区分・社員IDを変える場合は、選択先が利用中・有効であることを確認する。
- 該当する値を変更しない編集では、既存の停止場所・無効な社員への割当を保持できる。
- 復元でも、その機器が保持していた情報を維持できる。
- 外部キーを外したり、参照IDをNULLへ自動変更したりして対応しない。
- 入力時と保存時の間に利用状態が変わる場合があるため、保存時にも確認する。

### 12.2 最後の管理担当者

role=2かつis_active=1のアカウントが1人だけの場合、その人の無効化を拒否する。

複数の管理担当者を同時に無効化する操作でも0人にならないよう、同じトランザクションの中で必要な行をロックし、状態・件数を確認する初期案。画面表示時の件数だけでは判定しない。

初期版の既存アカウント編集は氏名のみとし、権限・ログインIDは変更できない【確定】。将来追加する場合も、降格によって有効な管理担当者が0人にならないよう同じルールを適用する。

### 12.3 一体で確定する更新

次を別々に確定しない。

- 採番と機器登録。
- 種別別の採番、機器の種別・番号更新、2項目の履歴。
- 場所・利用者・状態の更新と、変わった項目の履歴。
- 更新成功の判定、row_version更新、更新日時。

ロックを待つ競合やデッドロックでは、失敗したトランザクションをロールバックする。再試行の回数・画面メッセージは実装で定義し、失敗を保存成功として扱わない。
